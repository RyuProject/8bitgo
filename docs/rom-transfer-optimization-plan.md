# 游戏 ROM 上传与启动链路优化方案

更新日期：2026-11-26

## 目标与验收原则

覆盖管理员选文件、校验、上传、发布，以及玩家取模拟器核心、取 ROM、启动到首帧的完整链路。优化以真实传输耗时、首字节时间、失败重试量和成功启动率为准；不能通过放大内存峰值、丢续传能力、削弱校验或把不同版本字节拼接来换吞吐。每项优化都要同时验证 ROM 字节完整、核心能初始化、游戏能到首帧。

当前无法访问生产 R2 管理写权限，也没有可用的浏览器性能追踪面板。因此本方案区分代码/夹具可证实的结果与必须在真实浏览器、边缘节点或生产只读流量下测量的结果；不把离线耗时或协议推断写成线上提速百分比。

## 当前实现盘点

### 管理员上传

- 新上传默认直接发送明文 ROM；旧 8BG 导入会先解包。`GameForm.tsx` 当前 `shouldPack = false`，所以 ROM 打包器的 Zstd 等级不在当前常规后台上传路径上，盲目调低打包等级不会缩短这条路径。
- 上传由浏览器直达 ROM Worker / R2，不经过 Express 转发。小于 multipart 阈值的对象单发上传；大文件使用 8 MiB 分片、断点续传和本地文件指纹校验。
- 小文件单发 PUT 也用 45 秒无进展看门狗；上传请求体完成时最高显示 99%，只有 Worker 确认 key 与对象大小后才到 100%，静默断线不会让后台一直挂着。
- 分片任务由递增游标直接分配，不预先分配整份队列，也不对最多 10,000 个分片反复执行 `Array.shift()`；减少大文件上传时的队列搬移和临时数组。
- 首片先单路启动；累计上传约 1 MiB 且观测至少 250 ms 后，用真实进度估算上行，最多试探放行第二路。只有测速首片成功才升至按实测吞吐、设备内存与网络提示选择的 1–4 路；试探期出错立即收回并发，连接错误也会收敛并在成功后逐步恢复。若浏览器没有可用进度事件，则沿用完整首片测速。不同文件共用每浏览器页内的传输预算，最初上限按设备与省流量提示设定，网络故障后降为单路并逐步恢复。分片流式写入 Worker，不先把整片复制到 Worker 内存。
- PS1 多盘组原来逐盘等待；现在两个盘片上传任务可并行，但所有大文件分片仍共用总并发预算。进度按字节加权，M3U 只在全部盘片成功后发布，清单盘序仍按管理员选择顺序。
- PS1 多盘组任一盘失败会取消同组另一盘的在途请求并阻止继续派发分片；浏览器支持强摘要续传时保留已确认分片，下次同文件重试逐片核验后续传，否则安全清理会话，避免失败后仍白传剩余数百 MB。
- PS1 多盘组同页重试复用本次发布的随机目录；已完成盘片先用有 12 秒上限的对象探测核对存在和大小，吻合时跳过整张大盘的重传，探测失败则安全重传。换选文件、换游戏/语言或成功发布都会结束会话；不把 `File` 对象指纹跨页面持久化。
- 致命分片错误在并发闸释放排队任务前就会通知上传调度器；例如首片收到 403 时，不会再把后续最多三片（24 MiB）发上行。已在传分片仍会按结果入账，保留可续传行为。
- `effectiveType=3g` 只作为首片前的网络先验，不能在首片实测后仍把上传封顶两路；现由首片实测选择最高并发，Save-Data / 2G 仍单路，明确低内存或双核设备仍最多两路。浏览器未公开硬件并发数时按“未知”处理，不误判成双核。
- 上传早期进度只用于提前试探第二路；首片完整到达后会再用整片耗时校准目标并发，避免 XHR 缓冲造成的短时突发吞吐把后续并发错误推到 3–4 路，也确保早期估算较保守时可以上调。
- 创建请求具备幂等恢复；已完成分片的 ETag 账本每最多四片或一秒批量写入，切后台、离页、可续传失败和合并前强制刷盘。异常崩溃最多让最近四片安全重传；合并后核对对象大小才允许绑定。
- 续传账本原先只采样文件头 / 中 / 尾，局部修改可能躲过样本并混入旧分片。现在上传时并行计算每片的分层 SHA-256（每个摘要窗口 1 MiB，只多留一个窗口），续传时核验已完成片，只复用内容完全匹配的片；旧账本缺强摘要的片会安全重传。核验阶段会在管理员界面显示进度。localStorage 账本同时限 20 条和 1.5M 字符，避免大文件摘要把整笔 `setItem` 推过配额。
- 发现并修复的往返浪费：每片原先把 `partNumber` 放在查询串里，导致每片 URL 不同。Fetch 标准的预检缓存键包含 URL；因此即使服务端预检缓存时长为一天，浏览器也不能在不同片 URL 间复用该缓存。现在新 Worker 明确声明能力后，客户端把分片号放在 `X-8BG-Part-Number`，所有片共用 `uploadId` URL；旧 Worker 和旧账本继续走原查询串协议。新 Worker CORS 允许该头。
- 实测边界：回归验证了 URL 固定、分片号递增、合并成功和旧查询参数兼容；未在真实后台浏览器抓取 OPTIONS 数量，故预期从“每个不同分片 URL 需单独预检”降到同一上传会话复用缓存，实际请求数仍需线上测量。

### 玩家 ROM 下载

- `loadProgress.ts` 采用 8 MiB Range 分片，与边缘分块缓存对齐；根据实测吞吐自适应 1–4 路、比较可用线路、对弱/慢线路择优或换线，并支持有界并发写入与 IndexedDB 续传。
- 玩家 ROM 首段早期采样仍可提前预取，但正式并发在第一片完整接收后改用完整分片耗时重新校准；若完整样本低于早期估计，会立即取消超出正式并发的在途预取，避免它们继续抢占弱网带宽。
- 分片收到的响应头可能来自对冲备用域；线路负载现在在响应头落定后迁到实际服务域，对冲等待期间也计入备用域的在途请求，避免调度器把仍忙的线路当成空闲线路继续派片。负载打分沿用线路排序器的近期故障折扣，避免原始测速稍快但刚失败的线路在分片调度时反超。
- 线路分数在本页仍即时写入内存，供后续分片马上选路；跨访问 localStorage 持久化合并为每秒至多一次，并在离页 / 切后台时强制刷盘，避免每片完成都同步序列化并阻塞 ROM 正文处理。
- 慢线路触发备用域测速时，不再在主下载流的进度回调里等待探测；当前 ROM 流继续读，备用域若及时证明快 15% 以上才中止首片并切线。首片先完成时取消未返回的探测，避免小文件多等或后台留下无用请求。
- 8 MiB Range 与服务端 ROM / 街机 / NDS 缓存块对齐。未经过 EdgeOne / Worker Range、版本锁和缓存命中回归前，不改分片尺寸；否则可能把已验证的边缘缓存命中率和断点续传破坏掉。
- MAME CHD 悬停预热现在给网络读片和续传仓库读写都加了时限；停住的预热会释放同键任务槽。玩家点击开局时，正式下载会取消仍在路上的同键预热，避免两路重复拉同一 Range。
- ROM 下载退避等待在正常结束时会移除取消监听，已取消的信号也会立刻终止等待；PSP 整盘下载复用同一可取消等待，用户离开后不再等完整退避周期。
- 线路状态依据传输结果更新；内容错误与网络错误分开处理。ROM 内容损坏不能通过换语言或跨版本拼片掩盖。
- ROM 存在性缓存按结果设有效期：成功 ETag 5 分钟、确定缺失 1 分钟、经备用域得到的结论 5 分钟；同 key 覆盖 ROM 后不会永久沿用旧缓存版本，新上传对象也能从旧 404 恢复。
- 下载续传仓库配额不足时，原先只在分片写入成功后清理旧会话；四个未过期会话占满空间会让新 ROM 首片持久化失败，之后不再尝试续传写入。现配额失败会串行淘汰最旧的完整旧会话并重试一次，始终保留当前下载 key；无空间可回收时仍回退普通下载，不影响开局。
- 续传仓库的常规清理原先每写一片都扫描会话；MAME 的 OPFS 还会遍历目录并逐个读取元数据。现改为每 30 秒至多巡检一次，并合并在途巡检；配额失败仍绕过节流，立即清理并重试。夹具已验证普通写片不重复扫描、配额失败立即清理并能重试；生产浏览器负载效果待测。

### 模拟器核心下载与启动

- EmulatorJS 已自托管核心，具有下载超时、XHR 备用下载、严格长度/错误页校验、版本化 Range 续传、断流恢复、缓存代次和构建后产物校验。
- 核心预热受指针意图、设备和省流量状态控制；大型核心不会无差别地在触屏或弱网设备提前整包下载。
- 2026-11-26 只读核对公开目录中 2 个未加密 PS1 CHD：对 `rom.8bitgo.com` 发 `Range: bytes=0-31` 均返回准确 206/32 字节；两个 v5 头都含 `cdfl`，当前预测 PCSX 与最终核心选择一致。8BG 加密 CHD 的内层头未抽样，不据此宣称覆盖全部 CHD，也不为未经证实的少数格式推迟普遍预热。
- js-dos、Ruffle、PSP、PS2 等其他运行时各有独立加载路径。核心本身的网络耗时、解压/编译耗时、游戏启动耗时需要用阶段数据分开看，不能把“下载完成”当作“能玩”。

后台启动漏斗已用一次启动中的 `start_click`、`download_complete`、`first_frame`、`game_playable` 计算阶段均值和样本数，并按游戏、运行时、地区拆分。配对时排除逆序事件与跨运行时回退连接，避免误算运行时均值。`download_complete` 对非 HTML5 表示 ROM / 启动资源到手；对 HTML5 只表示 iframe 文档加载，仍不能拆出核心下载、ROM 下载和 WASM 实例化各自耗时。

本轮已把可观测阶段补入同一漏斗：ROM 首次进度到确认完整获取、EmulatorJS 核心预热开始到整份资源进入 HTTP 缓存、引擎 IndexedDB 核心命中次数，以及资源完成到运行时 `onReady`。后台按同一次启动配对后，可按游戏、运行时和地区查看；跨运行时回退、逆序时间会排除。光盘按需读取和 PSP 流式播放不伪造“整盘下载完成”。ROM 缓存读取可能在首次进度出现前已完成，因此缓存命中的 ROM 耗时可能接近 0，不能解释为真实本地读取时长。预热计时从本局开始等待该资源算起，若本局复用已有预热请求，显示剩余等待时间，不回溯到玩家悬停时的预热起点。

为避免性能观测本身增加开局往返，普通阶段由播放器暂存并合批发送：已有待发阶段时，下载完成、首帧或可玩事件会立即刷新批次；另有 15 秒兜底、失败和卸载刷新。常见情况下多个 ROM / 核心阶段会共用一次请求。失败、超时等诊断事件仍走原有单独接口。服务端限制批次最多 16 项，且必须属于同一访问与启动、阶段类型不得重复；批量落库使用一条 `INSERT IGNORE`，保留事件唯一键去重。播放器缓冲区按事件去重，批次请求失败时客户端撤销本地去重标记，允许生命周期内后续回调补报。

核心预热事件携带仅存在于内存中的核心标识，不上传资源 URL。一次 attempt 只选第一个核心作为统计样本；完成事件必须和选中的核心匹配，缓存命中和重复完成不会生成第二条阶段。这样自动换核心重试不会把旧核心的开始与新核心的完成配成一个虚假的长下载。

## 分阶段执行

### 阶段 1：消除可证明的请求开销（已完成代码改动）

- 使用能力协商把 multipart `partNumber` 移入请求头，固定同一上传的分片 URL。
- 每个已确认分片在续传时按强摘要校验；同名 / 同大小 / 同时间戳但局部字节不同的镜像，只重传不匹配片，不会静默合成两版 ROM。
- 保留旧 Worker、旧浏览器账本和查询参数模式；服务端校验查询参数与请求头冲突、非法值及错误方法，防止误落到普通 PUT/DELETE。
- 更新 standalone Worker 产物并增加客户端、Worker、CORS 预检回归。

### 阶段 2：形成真实链路基线

对每个阶段记录时间和结果：文件校验/街机识别、格式转换、首片、每片吞吐、并发变化、合并、ROM 首字节、ROM 完整下载、核心首次字节、核心解压/实例化、首帧。至少覆盖大陆与境外、桌面与手机、冷缓存与热缓存、慢上行与快上行。

上传耗时需区分“等待管理员选择文件”与“数据传输”；玩家加载需区分边缘/CDN 等待、传输、解压和核心启动。只记录聚合阶段耗时和文件大小档位，不记录 ROM 内容、完整对象 key、令牌或账号标识。拿到基线前不改并发上限、Range 大小或预热策略。

### 阶段 3：按瓶颈调上传

- 如果大文件在高带宽设备仍受请求数量限制，先对比 8 MiB 与更大分片在上行吞吐、失败重传字节、Worker 限制和 R2 最小分片规则上的净收益；只在成功率不退化时调整。
- 如果低速设备首片等待主导时间，验证“短测速窗口、仍满足 R2 非末片最小尺寸”的可行性；不能因缩短首片而造出 R2 无法合并的分片序列。
- 并发控制继续以首片真实上行及错误反馈为主，Network Information API 只作保守先验；设备内存低、Save-Data、2G 时保持低并发。
- 对上传失败复用现有幂等 ID 与文件指纹；重试只能续传同一内容，不能让两个浏览器并发写同一个最终 key 后静默覆盖。

### 阶段 4：按瓶颈调玩家 ROM 与核心下载

- ROM Range 大小、并发和线路对冲按真实分位数调整；以用户首帧延迟和完整率优化，不以下载器吞吐单指标优化。
- 对频繁玩的核心可测预热命中和浪费字节；只在用户表现出启动意图时优先预热，遵守省流量、后台标签页和设备内存限制。
- 对核心冷启动拆分网络、IDB 缓存、解压、WASM 初始化和第一帧。只有确认某个阶段主导后再优化该阶段；更换核心或引擎必须保留 ABI、语法、内容哈希、缓存代次和真实游戏首帧门禁。
- CDN/Worker 线路变化时，续传必须锁定强 ETag/内容版本，Range 偏移必须连续；不满足时丢弃旧前缀并完整重取。

### 阶段 5：用户操作与故障恢复

- 默认自动选安全 ROM、核心和线路；只有出现歧义时再让管理员选项，不因自动化猜测覆盖已有核心选择、街机包名或语言槽。
- 错误向用户指出可恢复动作；网络中断保留可续传状态，ROM 损坏/版本不匹配则停止并清理对应坏缓存，避免无限重试。
- 后台发布前完成上传大小/ETag 核验和平台专用校验；PS1/PSP 转换、DOS Sockdrive、街机 ROMset 等继续沿用各自原子发布/首帧保护流程。

- 已通过 `npm run test:r2-upload-client`，包含能力协商、稳定 URL、分片号、合并完整性、旧 Worker 路径、局部内容变更时重传差异片、相同片继续复用、无摘要旧账本安全迁移、大账本下最新续传状态仍能落盘，以及 3G 高速实测可升到四路、未知硬件信息不误限双核的回归。
- 本轮扩展 `npm run test:r2-upload-client`，验证首片致命鉴权失败后并发队列不再继续传输；修复闸门释放排队任务早于错误回传的竞态。

## 当前不建议盲改的项目

- 不把 `MAX_CONCURRENCY` 直接拉满：HTTP/2 重置、Worker 限流、手机内存和多路重试会抵消收益。
- 不更改 8 MiB ROM 下载 Range：它和现有边缘缓存块、断点续传和版本校验一一对应。
- 不降低或提高 Zstd 等级来宣称后台提速：当前后台常规上传禁用打包；旧包解密、服务端转换等路径应另用真实文件测量后再决定。
- 不合并不同核心 / ROM 下载器为单一大抽象：各引擎的缓存、ABI、错误语义和内容安全边界不同，压短代码本身不是性能收益。
