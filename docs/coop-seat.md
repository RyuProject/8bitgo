# 让观众上场当 2P（Flash 同屏双打 → 双人联机）

> 代码：`src/emulator/coopSeat.ts`（协议 + 闸）、`broadcast.ts`（房主）、
> `adapters/liveview.ts`（访客）、`LiveControls.tsx` / `LiveChat.tsx`（界面）。
> 回归：`npm run test:coop-seat`。

## 这是什么

森林冰火人这类游戏是**同屏双打**：一台机器、一个键盘，两个人各按一组键。
以前这种游戏在站上只能两个人挤一台电脑 —— 联机按钮不会出现，因为
`p2pPlayable()` 要求平台有 EmulatorJS 核心，而 Flash 跑的是 Ruffle。

这个功能换了条路：**游戏只在房主那一台跑，访客看直播画面、把按键发回来**。

    房主浏览器                                    访客浏览器
    ┌──────────────────────┐                  ┌──────────────────────┐
    │ Ruffle 跑游戏         │ ──WebRTC 音视频─► │ <video> 看画面        │
    │ sendButton(…, seat 1) │ ◄─DataChannel──── │ 屏幕手柄 / 键盘       │
    └──────────────────────┘                  └──────────────────────┘
                    └──── 只有握手经服务器 ────┘

## 为什么不是 netplay

EmulatorJS 联机难在**同步核心状态**：两边都在跑游戏，状态必须一致。
这里根本不需要 —— 访客从来不跑游戏。于是「没有联机能力」的引擎反而能凑出双人游戏。

三个前提在仓库里早就备好了，这个功能只是把它们接起来：

| 位置 | 早就有的东西 |
|---|---|
| `ruffle.ts` `dispatchKey` | 往 `<ruffle-player>` 派发合成 `KeyboardEvent`，**已上线在用**（屏幕手柄） |
| `ruffle.ts` `sendButton(b, down, seat)` | `seat === 1 → keys.p2`，注释写着「留给把观众提成 2P 那一步」 |
| `flashKeys.ts` `FlashKeys.p2` | 同屏双打游戏的第二组键位 |

## 通道

房主给每个观众建 PeerConnection 时，在 `createOffer()` **之前**加一条
`createDataChannel('coop')` —— 通道随 SDP 过去，不需要重新协商。访客侧只等
`ondatachannel`，**自己不建**（建了就是两条通道，房主收不到而访客以为发出去了）。

⚠️ 顺序错了没有任何报错：直播照常，只是「上场」那颗按钮永远不出现。有测试守着。

可靠 + 有序（DataChannel 默认值，不要改成 unreliable）：按键消息极小极稀，
而**丢一个 keyup 的代价是角色一直朝墙里跑**。

不走 socket.io：每次按键多一趟服务器往返，还给信令服务器加上按键量级的负载。
**代价**：服务端不知道座位状态，所以大厅暂时显示不出「这房还差一个人」。

## 协议

```
房主 → 访客   {t:'hello', coop:true, buttons:['up','left','right']}   通道一开就发
访客 → 房主   {t:'want'}                                             我想上场
房主 → 访客   {t:'seat', on:true, buttons:[...]}                     给你 / 收回
访客 → 房主   {t:'k', b:'left', d:true}                              一次按键
访客 → 房主   {t:'leave'}                                            我下场
```

**能力发现靠 hello，不靠猜**：访客不知道这一局是不是同屏双打游戏，猜错就是画一颗
按了没反应的按钮。老版本的房主不发 hello，访客收不到就当没有 —— 正好是安全的那一边。

## 安全：三条规则，都在 `coopSeat.ts` 里

1. **身份只来自「消息从哪条通道来的」。** 协议里没有座位号 / 玩家号字段。
   这是 `netplayGuard.ts` 那次事故的逐字复用：EmulatorJS 让访客自己填 `player`，
   于是任何访客都能替 1P 按键。服务器看不见 DataChannel，这道闸只可能在房主浏览器里守。
2. **限流**：按键 120/秒（键盘按到最快也就几十），`want`/`leave` 1/秒。
3. **按钮白名单**：协议层认八个抽象按钮，再按这一局 `keys.p2` 的键集过一遍。
   `coopButtons()` 返回空 = 这一局没有 2P 位 = 一个按键都不放行。

## 失败模式：松键

**漏一个 keyup，游戏里那个角色就一直朝墙里跑，而且看起来像游戏卡住了** ——
玩家不会想到是「刚才那个人下场了」。所以这几条路径全都要松键，一条都不能漏：

| 触发 | 谁负责 |
|---|---|
| 房主收回座位 / 访客点下场 | `gate.revoke()` 返回按着的键，`broadcast` 照着发 up |
| 访客断线、拆连接 | `dropPeer` → `gate.forget()`（**先松键再 close**） |
| 房主停播 | `stop()` 里先 `revokeInternal()` |
| 换人（座位给了另一个观众） | `gate.grant()` 返回上一位按着的键 |
| 访客切标签页 / 窗口失焦 | 访客侧 `blur` → `releaseCoopKeys()`（浏览器切走时**不发 keyup**） |
| 访客主动下场 | **先报松键再报 leave** —— 反过来的话房主已经收了座，那几条 up 会被闸丢掉 |

两边都做是有意的：访客主动下场那条路上房主是被动的，等他察觉之前那几百毫秒里键还按着。

## 访客侧几乎没有新界面

访客那个运行时就是 `liveview`，它的 `mount()` 返回的是正常的 `RuntimeHandle`。
拿到座位时它只做三件事：设 `padButtons`、加 `touchpad` 能力、`onCaps` 报一次 ——
**现成的 `TouchPad.tsx` 就自己出现了**，按下走 `sendButton`，和手机上玩单机同一条路。
桌面访客走键盘（`COOP_KEYMAP`：方向键 / WASD / Space），按下前判 `isTyping`（这一页上有弹幕框）。

抽象按钮层白赚一笔：访客按自己顺手的键，房主那边映射成这一局 2P 真读的键
（火娃冰娃是 A/W/D）—— **两边键位不用一致**，也不用告诉访客该按什么。

## 怎么试

1. A 电脑打开 `https://8bitgo.com/games/fireboy-and-watergirl`，开始游戏（会自动开播）
2. 从 📡 拿观看链接，B 电脑（或手机）打开
3. B 那边弹幕框旁边出现 👥「上场当 2P」→ 点它
4. A 那边同一个位置变成 👥「让 TA 上场」→ 点它
5. B 用方向键 / WASD（手机上是屏幕手柄）操作冰娃；A 用方向键操作火娃

对不上的时候按这个顺序查：
- B 那边没有 👥 → 房主的 `hello` 没到（通道没建起来？`coopButtons` 空？那款游戏没配 `p2`）
- 有按钮但按了没反应 → 看 A 的控制台 `[ruffle]`；或者座位没给（A 那边是不是还显示「让 TA 上场」）
- A 那边角色卡着一个方向 → 松键漏了，把上面那张表对一遍

## 还没做

- **大厅不显示空位**：纯客户端方案的代价。要做就是 `live.js` 的 `publicRoom` 加个字段 +
  `notifyRoomList()` 那一处调用，独立的一小步。
- **只有一个 2P 位**：`SeatGate` 现在是单座。三人以上的同屏游戏要把 `seat` 换成 Map。
- **延迟**：访客的按键要走一趟 WebRTC（同城几十毫秒，跨境一两百）。
  解谜平台跳跃能玩；格斗类不合适，别往那边推。
- **只有 Ruffle 报 `coopButtons`**：html5 那一路的按键注入没做（跨源 iframe 大多读不到）。
