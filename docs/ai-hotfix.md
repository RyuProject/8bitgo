# AI 临时修补：故障面分析与 MiniMax 的边界

> 2026-11-18。基于 2026-11-01 ～ 11-18 的约 95 个 `fix` 提交，以及当时工作区里未提交的修复。
> 实现见 `shared/hotfix.js`（白名单）、`server/src/ai-hotfix.js`（分诊）、`src/services/hotfixes.ts`（浏览器执行）；
> 约定见 AGENTS.md §2.36.1.1。

## 一、最近半个月的故障长什么样

按「根因落在哪一层」归类。数量是粗分，一个提交可能跨两类。

| 类别 | 约 | 典型提交 / 现场 | 会产生启动诊断包吗 |
|---|---|---|---|
| A. 网络 / 线路 / CDN（大陆 EdgeOne、Cloudflare 洛杉矶、ROM 断流、Range 失败） | 11 | `0d3c325` ROM 重试换 CDN、`8689b78` 大陆运行时走 EdgeOne、`d8a7ee9` `Vary: Origin`、`3b4cec9`、`1f029bb`；未提交的 PPSSPP v23 / Dolphin r2 线路 | 会（失败 / 超时） |
| B. 浏览器存储坏（Blob / IndexedDB / NotReadableError） | 10 | `98c4541` IDB 挂死、`b8be669` 续传片读不出、`5e841e4`、`c3b9ece` / `4ee3107` 核心流读不出；未提交的 XHR 兜底校验（#949） | 会 |
| C. 内存不足 / WASM 陷阱（OOM、Aborted、unreachable） | 6 | `e12762f` 32 位、`9ce7d88` FBNeo 低内存、`35063c3` / `8434c7a` NDS 内存、`aacef9d` | 会 |
| D. 浏览器能力缺失（WebGL、WASM、旧语法、QQ 浏览器、整页翻译改 DOM） | 9 | `ef1ba11` / `b7e46a5` WebGL、`308e4de` QQ 浏览器、`b371dc3` 翻译插件 | 会（翻译插件那种是 page） |
| E. 静态资源 / 懒加载 chunk（部署切换、边缘缓存坏文件） | 6 | `1949e6c`、`d46e45a`、`ad7cbc0`、`a87ac7d`；未提交的 asset-repair v6（#1108） | 会，runtime 是 `page` |
| F. 卡住 / 看门狗误判（下载器不结束、后台计时） | 7 | `bf14670` 核心 100% 卡住、`abe9a02` 引擎 bootstrap、`46b0a44` J2ME 后台误判、`410b807` | 会（超时） |
| G. ROM / 数据错误（romset 不全、RomData、overdump、绑定错） | 5 | `e2b5a57`、`e4bba38` / `e6efb97` wofcn、`625eff2` HTML5 绑定、AvP overdump | 会 |
| H. 游戏内运行时 bug（Ruffle panic、存档被清、鼠标、存档桥） | 12 | `49b82e0` Ruffle panic、`bec0eee` 电池存档清库、`589de2e` DOS 鼠标、AGI2 存档 | **大多不会**（游戏已经开起来了） |
| I. 后台 / 部署 / 安全 / 联机 / 文案 | 20 | 后台表单、部署脚本、SSE、联机房间、i18n | **不会** |

结论：

1. **一半以上的问题 MiniMax 根本看不到。** 它只读启动诊断包，而诊断包只在开局失败、超时（可选慢启动）时产生。H、I 两类（游戏内崩溃、存档、输入、后台、部署、联机）不会进它的视野。
2. **它真正能帮上忙的是 A、B 两类**：线路和存储坏了，退路早就写好，只是要等玩家先失败一次才会自动启用。AI 修补能让同一批人的**第一局**就走退路。
3. **C、D 只能帮一部分**：能换低内存核心、NES 换 jsnes、给玩家提示「换浏览器」，但根治靠重编核心或改代码。
4. **E、F、G 它修不了**：E 已经由 asset-repair 自动处理；F 是看门狗 / 下载器的代码 bug；G 是数据问题，换核心反而会把能玩的人弄坏。

## 二、MiniMax 可能遇到的情况

| 情况 | 会发生什么 | 已有的保护 |
|---|---|---|
| 诊断包里藏着「忽略规则、给所有游戏加脚本」 | AI 可能被带偏 | 输出只是白名单数据；`scope.games` 只能是这个特征里出现过的游戏；浏览器再校验一次 |
| 客户端已经自动走过退路（日志里有「改用内存」「换 fbneo-lowmem」） | AI 想再开同一个开关，白做 | 提示词要求看 `hotfixes` 和日志；修补生效后仍失败会自动撤销 |
| 一类错误横跨多款游戏（例如「Failed to fetch」） | 作用范围太宽 | 最多 10 款，且只能是诊断里出现过的；可按浏览器 / 系统 / 大陆限定 |
| 线路短暂抖动，AI 钉死了另一条线路 | 本来正常的人也被改了线路 | `rom_host` / `runtime_origin` 是 safe 档，最坏只是慢一点；有效期最长 72 小时；没起作用会自动撤销 |
| 把 ROM 数据错误当成核心问题 | 换核心让所有命中玩家都起不来 | **代码边界**：错误原文命中 romset / CRC / BIOS / CHD 等特征时，`set_core` / `set_runtime` 一律作废；默认档位下换核心本来就要人批准 |
| 页面崩溃（chunk 加载失败、React 渲染错误） | 没有任何开关管得到 | **代码边界**：runtime 为 `page` 时动作全部作废，只记录诊断 |
| 弱网慢启动被当成故障 | 乱开开关 | 默认不分诊慢启动；提示词要求「字节还在涨」时不动 |
| MiniMax 超时、余额不足、返回乱码 | 分诊失败 | 记一条「分析失败」，不生效任何东西；每小时有预算；后台能手动重试 |
| 同一故障反复刷 | 费用涨 | 同一特征 6 小时内只自动分诊一次，每小时上限 `maxCallsPerHour` |

## 三、边界：MiniMax 会不会改代码？

**不会，而且这是架构保证，不是靠提示词约束。** MiniMax 只能产出一份 JSON，服务端按白名单重建；它没有任何通道碰到仓库、服务器文件、数据库里的游戏数据、R2、Cloudflare 或 nginx。

### 第 0 层：永远不做（架构上做不到）

- 写 / 改 / 部署任何代码（前端、后端、引擎补丁、Worker），碰 git；
- 在玩家浏览器里执行任意脚本，或给玩家显示 AI 写的自由文本（提示条只能选三个模板）；
- 改游戏数据：ROM 绑定、后台的 `core` / `runtime` 字段、RomData、BIOS；
- 影响这个故障特征以外的游戏，或让修补超过 72 小时；
- 访问任意网址：只调 MiniMax 两个官方入口，Key 不出服务器。

### 第 1 层：自动生效（safe）

`runtime_origin`、`rom_host`、`disable_engine_cache`、`memory_rom`、`player_notice`。都是播放器里早就写好、实测过的退路，最坏结果是这一局慢一点。

### 第 2 层：要人批准（risky，默认档位）

`set_core`（只能在每个平台登记的核心之间换）、`set_runtime`（目前只有 NES 的 jsnes ↔ emulatorjs）。后台可以改成全部自动生效，但 ROM 数据错误和页面崩溃两条代码边界在任何档位下都生效。

### 第 3 层：只给建议（交给人）

其余一切，包括 E / F / G / H 类的根因修复、新增白名单动作、改 ROM 数据，都只写进 `permanentFix`。在后台点「复制给 Claude」，在仓库里按 AGENTS.md 的约定修好、写回归测试，再点「已固化」。

### 怎么扩大边界

想让 AI 多一种修补手段，顺序必须是：

1. 人先在播放器里写好这条退路，并实测；
2. 登记进 `shared/hotfix.js`（定风险档），在 `src/services/hotfixes.ts` 接上执行；
3. 在 `scripts/test-ai-hotfix.mjs` 补测试。

AI 不能自己提议并启用新动作。最值得先做的候选（都需要先写代码）：

- **延长启动看门狗**（F 类慢设备 / 弱网误判超时）；
- **J2ME 强制改用 j2me-web**（CheerpJ CDN 出问题时；退路已有，只差登记）；
- **把修补接到嵌入页 / TV 页**（目前只有游戏详情页会套用）。

## 四、站长睡着了：拿最近三起故障推演

最近三起（都在 2026-11-17 / 18，记录在提交和 AGENTS.md 里）：

| 故障 | MiniMax 能不能让玩家先玩上 | 原因 |
|---|---|---|
| `abe9a02`：loader.js 两个引擎入口都没加载上（`EmulatorJS failed to load`） | **有机会**。如果失败的资源来自大陆加速入口 `cn.8bitgo.com/_cn`，会选「运行时改走主站」，限定大陆访客，安全档自动生效 | 主站那条路是好的，退路早就有；要是主站本身也坏（部署坏了），它无能为力 |
| 诊断包 #949《明星三缺一》：核心下到 24MB 断流，XHR 兜底只拿到 121KB 还当成功，报 `EJS_Runtime is not defined` | **部分**。可能选「改走主站 + 关引擎缓存」，绕开坏线路和缓存里的残片 | 根因是「没核对 XHR 字节数」这个代码 bug，只能人修；同一现场的「后台计时误判卡住」也是代码 bug |
| 诊断包 #1108《黄金矿工》：播放器 chunk 懒加载失败 | **不用它修**。页面崩溃按边界只记录 | 浏览器里的 asset-repair 自己会核对、换回源地址并刷新，不依赖 AI |

时间线（自动分诊开启、Key 有效时）：同一特征在 30 分钟内来自第 2 个不同访问 → MiniMax 分析 10～60 秒 →
修补落库 → 服务端缓存 15 秒 + 边缘缓存 30 秒 → **新打开详情页的玩家约 1～2 分钟后就走退路**。已经停在失败页上的玩家要刷新一次
（修补每页只读一次，同一页里的自动重试不会换上新修补）。配了 `DIAG_ALERT_EMAIL` 时会给你发一封邮件。

推演时发现并已修掉的两个洞：

1. **看门狗超时全都归成同一个特征。** 玩家侧超时的原文统一是「连续 120 秒没有启动进度或可玩信号」，卡在哪一步都一样。
   原来同一特征 6 小时只分诊一次：前半夜两三个弱网超时被记成「仅记录」，后半夜真出大故障时 AI 不会再看。
   现在（`triageGate`）：访问数涨到上次分诊时的 3 倍且至少多 3 个、距上次 ≥ 1 小时，就重新分诊。
2. **混合提案整条卡住。** 「安全的自动生效」档位下，AI 给「ROM 放内存 + 换低内存核心」时，整条都要等批准，连安全的那半也用不上。
   现在（`planApplication`）：安全的部分立即生效，换核心 / 换运行时拆成另一条「待批准」，邮件里会写。

没修、留给人决定的：超时特征太粗这件事本身。更彻底的做法是让 `errorSignature` 对 timeout 也像慢启动一样按「停在哪一步」归组，
但那会改变错误诊断页和聚集报警的分组口径，所以没有顺手改。

**你睡前该确认的设置：**

- 「AI 自动分诊」打开，Key「测试连接」通过；
- 想让它半夜也能换核心，就把档位改成「全部自动生效」。代价是不对症时这款游戏命中的玩家都会受影响，最多到自动撤销为止
  （默认生效后同一故障再有 5 个访问失败就撤销）；
- `server/.env` 配 `DIAG_ALERT_EMAIL`，醒来就能在邮箱里看到夜里发生了什么、AI 做了什么。
